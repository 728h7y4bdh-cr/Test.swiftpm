## 0. 本書について

本書は、本プロジェクト（Sample App）のSwiftコードに適用するコーディング規約を定義する。以下の観点を軸に構成する。

1. 機能単位でのクラス名・関数名・変数名の統一
2. 各機能間の癒着防止
3. 保守性・変更への強さ

## 1. 命名規則

### 1.1 型名（class / struct / enum / protocol）

型名の先頭を大文字にし、単語の区切りごとに先頭を大文字にする表記（**UpperCamelCase**。例：`ConnectionViewController`）とする。型が「要件定義書上のどの処理・どの役割に対応するか」が名前から判別できるようにする。

| 分類 | 命名パターン | 例 |
|---|---|---|
| 画面（ViewController） | `<画面名>ViewController` | `TopViewController`, `ConnectionViewController`, `SendViewController`, `ReceiveViewController` |
| 複数の画面が共通で継承する基底クラス | `<用途>BaseViewController` | `CommunicationBaseViewController` |
| 要件定義書の「処理」に対応する機能レイヤークラス | 要件定義書の処理名を英語化してそのままクラス名にする | `ConnectionStartHandshake`（通信開始処理）, `ListenStartHandshake`（待受開始処理）, `Disconnector`（通信切断処理）, `DataSender`（データ送信処理）, `DataReceiver`（データ受信処理）, `AppInitializer`（初期化処理） |
| Core Bluetoothとの接続を担う役割レイヤークラス | `<役割>Session` | `BluetoothCentralSession`, `BluetoothPeripheralSession` |
| アプリ全体の状態・パラメータを一元管理するクラス | `<管理対象>Manager` | `StatusManager`, `BluetoothManager` |
| 呼ばれた瞬間に1回だけ確認・判定を行い、結果を返して役目を終えるクラス | `<確認したい対象>Checker` | `BluetoothAuthorizationChecker` |
| 内部パラメータ・値を保持するモデル | 対象を表す名詞1語とする（動詞・接尾辞は付けない） | `Payload`, `AppParameters`, `AppStatus` |
| バイト列⇔モデルの変換など、状態を持たない変換ロジック | `<対象>Codec` | `PayloadCodec` |
| デリゲートプロトコル | `<提供元の型名><通知内容>Delegate` | `BluetoothManagerReceiveDelegate`, `BluetoothManagerConnectionDelegate` |
| デバッグ用の設定値を保持する型 | `<用途>Settings` | `DebugSettings` |
| デバッグ用のログ出力を行う型 | `<用途>Logger` | `PreviewBypassLogger` |
| アプリ全体のどこからでも呼び出せる汎用ユーティリティ（継承を使わない） | `Common<用途>` | `CommonUtility` |

同じ分類に属する型は、上記パターンから外れる命名をしない（例：画面クラスを`XxxScreen`のような別パターンで命名しない）。

「複数の画面が共通で継承する基底クラス」と「アプリ全体のどこからでも呼び出せる汎用ユーティリティ」はどちらも共通処理をまとめる型だが、実装方法が異なる。前者は画面（`UIViewController`）だけが対象のため継承（クラス）で実現し、後者はSwiftが多重継承をサポートしないため、どんなクラスからも使えるよう継承を使わない`enum`＋`static func`で実現する。

### 1.2 メソッド・関数名

先頭を小文字にし、以降の単語の区切りごとに先頭を大文字にする表記（**lowerCamelCase**。例：`startConnecting`）とし、動詞から始める。

- ユーザー操作（ボタンタップ等）のハンドラは`didTap<コントロール名>`で統一する（例：`didTapConnect`, `didTapBack`, `didTapSend`）。画面によって命名パターンを変えない。
- 一覧・変換・判定などの補助関数は、処理内容が動詞で明確にわかる名前にする（例：`presentAlert`, `matches`, `logIfNeeded`）。

### 1.3 真偽値（Bool）

- 変数・プロパティ名は`is`または`has`で始める（例：`isProcessing`, `isSending`, `isReceiving`, `isStopping`, `isPreviewBypassEnabled`）。
- 二重否定になる命名（例：`isNotReady`）は避ける。

### 1.4 クロージャ型のイベント通知プロパティ・デリゲート

- `on<イベント名>`で統一する（例：`onReady`, `onFailure`, `onDetect`, `onNotDetect`, `onWriteReceived`）。
- デリゲートプロトコルのメソッド名は`<型名の主語>did<結果>`の形にする（例：`bluetoothManagerDidFailToDetect`, `bluetoothManagerDidDisconnectUnexpectedly`）。

### 1.5 定数

独立したグローバル定数は作らず、関連する型の`static let`として定義する（例：`Payload.totalLength`, `Payload.idLength`）。定数の意味とその定数が属するデータ構造が、型名を介して結びつくようにする。

### 1.6 グローバル変数（アプリ全体で共有する状態）

- アプリ全体で共有する状態は、必ず専用の管理クラスの`static let shared`インスタンス（**シングルトン**。アプリ内でそのクラスのインスタンスを1つだけに限定する作り方）を介して宣言する。トップレベルに直接`var`／`let`を書く形は使わない。
- インスタンスを持たない静的な定数・設定（GATTのUUID定義、デバッグフラグ等）は、`enum`を使い、`型名.プロパティ名`の形で宣言する（例：`BluetoothGATT.serviceUUID`, `DebugSettings.isPreviewBypassEnabled`）。この場合もインスタンス化はせず、必ず型名を介してアクセスする。
- 参照は常に`型名.shared.プロパティ名`または`型名.プロパティ名`の形になる（例：`StatusManager.shared.status`, `AppParameters.shared.myID`, `BluetoothManager.shared.startConnecting(...)`）。

### 1.7 ローカル変数（関数内で完結する値）

- 関数のパラメータ・その場限りの変数は、型名接頭辞のないlowerCamelCaseで宣言する（例：`myID`, `targetID`, `success`, `payload`, `completion`）。
- `shared`という語や、管理クラスの型名を接頭辞として付けない。単なる識別子として宣言する。
- グローバルなプロパティと同名になること（例：`AppParameters.shared.myID`を読み取った一時変数`myID`）は問題ない。1.6の宣言形式とは書き方そのものが異なるため、混同は起きない。

## 2. 各機能の癒着防止

### 2.1 共有状態への書き込みは管理クラス経由に限定する

- 共有状態（ステータス、内部パラメータ等）を書き換える処理は、各機能が個別に直接値を代入するのではなく、必ずその状態を管理する専用クラスが提供するAPIを経由する。
- 状態遷移のように「ルール」を伴う値は、単純なsetterではなく、名前付きイベントを受け取って遷移先を決定するAPIを用意し、遷移ルールの実体（テーブル）を管理クラス1箇所に集約する（例：`StatusManager.apply(_ event: AppStatusTransitionEvent)`）。呼び出し側は「何が起きたか（イベント）」を渡すだけとし、「その結果どの値になるか」を各機能が個別に判断・指定しない。
- `apply`を呼ぶ場所（呼び出し箇所）が複数の機能に分散すること自体は許容する。各機能が要件定義書上の遷移契機を最もよく知っている場所（＝その処理自身の中）で通知するのが自然なため。許容されないのは、遷移ルール（テーブル）そのものが複数箇所に重複して存在することである。

### 2.2 1クラス1責務・1処理

- 1つのクラスが担当する処理は、要件定義書上の1つの「処理」単位に対応させる。複数の処理のロジックを1つの関数・1つのクラスに混在させない（例：ハンドシェイクの照合ロジックとデータ受信のチェックロジックを同じ関数に書かない）。
- 「役割」（誰が／どの経路で通信するか）と「機能」（何をするか）は別レイヤーに分離する。
  - 役割レイヤー（`BluetoothCentralSession`, `BluetoothPeripheralSession`）は、CoreBluetoothとの接続・送受信という「運び方」のみを担当する。BLE自体の通信処理はCore Bluetoothライブラリが行うため、役割レイヤーはそのAPIを呼び出すだけであり、ペイロードのバイトフォーマットや、ハンドシェイクの照合条件といった、アプリケーション独自の通信内容は解釈しない。
  - 機能レイヤー（`ConnectionStartHandshake`, `ListenStartHandshake`, `DataSender`, `DataReceiver`）は、そのアプリケーション独自の通信内容（ペイロードのバイトフォーマットやハンドシェイクの照合条件）を扱うが、CoreBluetooth自体の型（`import CoreBluetooth`）に依存しない。役割レイヤーが提供するクロージャベースの窓口（`Data`の送受信）のみを介して動作する。
  - 上記2レイヤーを組み合わせるのは調停役（`BluetoothManager`。複数の処理を裏で指揮する役目の呼び名としてCoordinatorとも呼ぶ）のみの責務とし、調停役自身はアプリケーション独自の通信内容を持たない。

### 2.3 公開APIの安定性

画面（ViewController）に対して公開するAPI（例：`BluetoothManager`の`startConnecting`等）のシグネチャは、内部実装（クラス分割・処理の委譲先）を変更しても変えない。内部構成の変更が呼び出し側に波及しないようにする。

## 3. 保守性・変更への強さ

### 3.1 ファイル構成

- 1ファイルにつき1つの主たる型を配置することを原則とする。ただし、以下のように主たる型と不可分な小さな随伴型は同一ファイルに含めてよい。
  - 主たる型の内部でのみ意味を持つ小さなenum（例：`Payload.swift`内の`PayloadType`・`CommunicationType`、`StatusManager.swift`内の`AppStatusTransitionEvent`）
  - 主たる型が実装先となるデリゲートプロトコル（例：`BluetoothManager.swift`内の`BluetoothManagerReceiveDelegate`・`BluetoothManagerConnectionDelegate`）
  - 逆に、互いに独立した別の責務を持つ型を1つのファイルにまとめることはしない。
- ディレクトリ構成は責務ごとに分ける。

  | ディレクトリ | 用途 |
  |---|---|
  | `Sources/`直下 | アプリのエントリポイント（`AppDelegate.swift`, `SceneDelegate.swift`）のみを置く。UIKitの仕様上、アプリ起動時にOSから最初に呼ばれるこの2ファイルは、他のどの責務分類（Models/Managers/ViewControllers/Debug）にも属さないため、専用のサブディレクトリを作らずルート直下に置く |
  | `Sources/Models/` | データ構造・値型（状態を持たないモデル） |
  | `Sources/Managers/` | ビジネスロジック（非UI）。役割レイヤー・機能レイヤー・調停役・状態管理を含む |
  | `Sources/ViewControllers/` | 画面 |
  | `Sources/Debug/` | 開発時のみのデバッグ機能（`#if DEBUG`で完全に囲う） |

### 3.2 アクセス制御

- 既定は`private`（同じ型の内部からのみアクセス可能にする修飾子）とし、外部に公開する必要があるものだけ明示的にアクセスレベルを緩める。
- シングルトンは`private init()`（型の外部からのインスタンス生成を禁止する書き方）により、外部からの多重インスタンス化を禁止する。

### 3.3 デバッグ専用コード

- 正式仕様に存在しないデバッグ専用のコードは、必ず`#if DEBUG`（Debugビルドの時だけコンパイル対象にする条件コンパイル文。Release／配布ビルドには含まれない）で囲む。
- デバッグ機能の有効／無効フラグは、機能ごとに個別のファイルへ分散させず、`Sources/Debug/DebugSettings.swift`に集約する。これにより、現在有効なデバッグ機能を1ファイルだけで把握・調整できる。

### 3.4 設計書とのトレーサビリティ

- すべての型・主要メソッドに、対応する設計書（要件定義書／PS設計書／SS設計書／UI設計書）の章・節番号を明記したコメント（`///`）を付与する。実装のどの部分がどの仕様に対応するかを、コードを見るだけで追跡できるようにする。
- ファイル内を複数のセクションに分ける場合（特に100行を超える、または複数の関心事＝Public API／Private実装／デリゲート準拠が混在するファイル）は、`// MARK: -`コメントで区切り、対応する設計書の章番号をあわせて記載する。1〜2メソッド程度の小さな単一責務ファイルでは、MARK分割を省略してよい。
