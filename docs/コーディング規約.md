## 0. 本書について

本書は、本プロジェクト（Sample App）のSwiftコードに適用するコーディング規約を定義する。既に実装済みのコード（PS/SS/UI設計書に基づく実装）で一貫して用いられている慣習を明文化したものであり、今後の機能追加・保守作業もこの規約に従う。

規約は以下4つの観点を軸に構成する。
1. 機能単位でのクラス名・関数名・変数名の統一
2. グローバル変数とローカル変数の区別がつく命名
3. 各機能間の癒着防止
4. 保守性・変更への強さ

## 1. 命名規則（機能単位での統一）

### 1.1 型名（class / struct / enum / protocol）

UpperCamelCase（先頭大文字）とし、型が「要件定義書上のどの処理・どの役割に対応するか」が名前から判別できるようにする。

| 分類 | 命名パターン | 例 |
|---|---|---|
| 画面（ViewController） | `<画面名>ViewController` | `TopViewController`, `ConnectionViewController`, `SendViewController`, `ReceiveViewController` |
| 要件定義書の「処理」に対応する機能レイヤークラス | 要件定義書の処理名を英語化してそのままクラス名にする | `ConnectionStartHandshake`（通信開始処理）, `ListenStartHandshake`（待受開始処理）, `DataSender`（データ送信処理）, `DataReceiver`（データ受信処理） |
| Core Bluetoothとの接続を担う役割レイヤークラス | `<役割>Session` | `BluetoothCentralSession`, `BluetoothPeripheralSession` |
| アプリ全体の状態・パラメータを一元管理するクラス | `<管理対象>Manager` または 意味の通る名詞 | `StatusManager`, `BluetoothManager`（調停役/Coordinator） |
| 内部パラメータ・値を保持するモデル | 名詞のみ | `Payload`, `AppParameters`, `AppStatus` |
| バイト列⇔モデルの変換など、状態を持たない変換ロジック | `<対象>Codec` | `PayloadCodec` |
| デリゲートプロトコル | `<提供元の型名><通知内容>Delegate` | `BluetoothManagerReceiveDelegate`, `BluetoothManagerConnectionDelegate` |
| デバッグ専用の設定・ロジック | 用途がひと目で分かる名詞 | `DebugSettings`, `PreviewBypassLogger` |

同じ分類に属する型は、上記パターンから外れる命名をしない（例：画面クラスを`XxxScreen`のような別パターンで命名しない）。

### 1.2 メソッド・関数名

- lowerCamelCaseとし、動詞から始める（例：`startConnecting`, `disconnect`, `sendData`, `normalizedID`）。
- ユーザー操作（ボタンタップ等）のハンドラは`didTap<コントロール名>`で統一する（例：`didTapConnect`, `didTapBack`, `didTapSend`）。画面によって命名パターンを変えない。
- 一覧・変換・判定などの補助関数は、処理内容が動詞で明確にわかる名前にする（例：`presentAlert`, `matches`, `logIfNeeded`）。

### 1.3 真偽値（Bool）

- 変数・プロパティ名は`is`または`has`で始める（例：`isProcessing`, `isSending`, `isReceiving`, `isStopping`, `isPreviewBypassEnabled`）。
- 三項化・二重否定になるような命名（例：`isNotReady`）は避ける。

### 1.4 クロージャ型のイベント通知プロパティ

- `on<イベント名>`で統一する（例：`onReady`, `onFailure`, `onDetect`, `onNotDetect`, `onWriteReceived`）。
- デリゲートプロトコルを使う場合は、メソッド名を`<型名の主語>did<結果>`の形にする（例：`bluetoothManagerDidFailToDetect`, `bluetoothManagerDidDisconnectUnexpectedly`）。

### 1.5 定数

- 独立したグローバル定数は作らず、関連する型の`static let`として定義する（例：`Payload.totalLength`, `Payload.idLength`）。定数の意味とその定数が属するデータ構造が名前空間で結びつくようにする。

## 2. グローバル変数とローカル変数の区別

### 2.1 グローバル（アプリ全体で共有する）状態

- アプリ全体で共有する状態は、必ず専用の管理クラスの`static let shared`インスタンス（シングルトン）を介してアクセスする。トップレベルの`var`／`let`（裸のグローバル変数）は一切使用しない。
- 参照は常に`型名.shared.プロパティ名`の形になる（例：`StatusManager.shared.status`, `AppParameters.shared.myID`, `BluetoothManager.shared.startConnecting(...)`）。
- インスタンスを持たない静的な定数・設定（GATTのUUID定義、デバッグフラグ等）は、`enum`を名前空間として使い、`型名.プロパティ名`の形でアクセスする（例：`BluetoothGATT.serviceUUID`, `DebugSettings.isPreviewBypassEnabled`）。この場合もシングルトンと同様、必ず型名を介してアクセスし、裸の変数にしない。

この規則により、コード中に `Xxx.shared.yyy` または `Xxx.yyy` という記述があれば、それはアプリ全体で共有される状態への参照であると常に判別できる。

### 2.2 ローカル変数・パラメータ

- 関数のパラメータ・ローカル変数は、型名接頭辞をつけないlowerCamelCaseとする（例：`myID`, `targetID`, `success`, `payload`, `completion`）。
- ローカル変数名がグローバルな管理クラスのプロパティ名と同じになる場合がある（例：`myID`という名前のローカル変数と、`AppParameters.shared.myID`）。これは意図的な許容であり、値の受け渡し（`AppParameters.shared.myID`を読み取って一時変数`myID`に代入する等）でよく起こる。区別は前述の「必ず`型名.`を介する」というアクセス規則そのもので担保する。

## 3. 各機能の癒着防止

### 3.1 グローバル状態への書き込みは管理クラス経由に限定する

- グローバルな状態（ステータス、内部パラメータ等）を書き換える処理は、各機能が個別に直接値を代入するのではなく、必ずその状態を管理する専用クラスが提供するAPIを経由する。
- 特に、状態遷移のように「ルール」を伴う値は、単純なsetterではなく、名前付きイベントを受け取って遷移先を決定するAPIを用意し、遷移ルールの実体（テーブル）を管理クラス1箇所に集約する（例：`StatusManager.apply(_ event: AppStatusTransitionEvent)`）。呼び出し側は「何が起きたか（イベント）」を渡すだけで、「その結果どの値になるか」を各機能が個別に判断・指定してはならない。
- 呼び出し箇所（`apply`を呼ぶ場所）が複数の機能に分散すること自体は許容する。各機能が要件定義書上の遷移契機を最もよく知っている場所（＝その処理自身の中）で通知するのが自然なため。**許容されないのは、遷移ルール（テーブル）そのものが複数箇所に重複して存在すること**である。

### 3.2 1クラス1責務・1処理

- 1つのクラスが担当する処理は、要件定義書上の1つの「処理」単位に対応させる。複数の処理のロジックを1つの関数・1つのクラスに混在させない（例：ハンドシェイクの照合ロジックとデータ受信のチェックロジックを同じ関数に書かない）。
- 「役割」（誰が／どの経路で通信するか）と「機能」（何をするか）は別レイヤーに分離する。
  - 役割レイヤー（`BluetoothCentralSession`, `BluetoothPeripheralSession`）は、CoreBluetoothとの接続・送受信という「運び方」のみを担当し、ペイロードのバイトフォーマットや、ハンドシェイクの照合条件といった「プロトコルの意味」を知らない。
  - 機能レイヤー（`ConnectionStartHandshake`, `ListenStartHandshake`, `DataSender`, `DataReceiver`）は、プロトコルの意味を扱うが、CoreBluetooth自体の型（`import CoreBluetooth`）に依存しない。役割レイヤーが提供するクロージャベースの窓口（`Data`の送受信）のみを介して動作する。
  - 上記2レイヤーを組み合わせるのは調停役（`BluetoothManager`）のみの責務とし、調停役自身はプロトコルの中身を持たない。

### 3.3 公開APIの安定性

- 画面（ViewController）に対して公開するAPI（例：`BluetoothManager`の`startConnecting`等）のシグネチャは、内部実装（クラス分割・処理の委譲先）を変更しても変えない。内部構成の変更が呼び出し側に波及しないようにする。

## 4. 保守性・変更への強さ

### 4.1 ファイル構成

- 1ファイルにつき1つの主たる型を配置することを原則とする。ただし、以下のように主たる型と不可分な小さな随伴型は同一ファイルに含めてよい。
  - 主たる型の内部でのみ意味を持つ小さなenum（例：`Payload.swift`内の`PayloadType`・`CommunicationType`、`StatusManager.swift`内の`AppStatusTransitionEvent`）
  - 主たる型が実装先となるデリゲートプロトコル（例：`BluetoothManager.swift`内の`BluetoothManagerReceiveDelegate`・`BluetoothManagerConnectionDelegate`）
  - 逆に、互いに独立した別の責務を持つ型を1つのファイルにまとめることはしない。
- ディレクトリ構成は責務ごとに分ける。

  | ディレクトリ | 用途 |
  |---|---|
  | `Sources/Models/` | データ構造・値型（状態を持たないモデル） |
  | `Sources/Managers/` | ビジネスロジック（非UI）。役割レイヤー・機能レイヤー・調停役・状態管理を含む |
  | `Sources/ViewControllers/` | 画面 |
  | `Sources/Debug/` | 開発時のみのデバッグ機能（`#if DEBUG`で完全に囲う） |

### 4.2 アクセス制御

- デフォルトは`private`とし、外部に公開する必要があるものだけ明示的にアクセスレベルを緩める。
- シングルトンは`private init()`により外部からの多重インスタンス化を禁止する。

### 4.3 デバッグ専用コード

- 正式仕様に存在しないデバッグ専用のコードは、必ず`#if DEBUG`で囲む。
- デバッグ機能の有効／無効フラグは、機能ごとに個別のファイルへ分散させず、`Sources/Debug/DebugSettings.swift`に集約する。これにより、現在有効なデバッグ機能を1ファイルだけで把握・調整できる。

### 4.4 設計書とのトレーサビリティ

- すべての型・主要メソッドに、対応する設計書（要件定義書／PS設計書／SS設計書／UI設計書）の章・節番号を明記したコメント（`///`）を付与する。実装のどの部分がどの仕様に対応するかを、コードを見るだけで追跡できるようにする。
- ファイル内を複数のセクションに分ける場合（特に100行を超える、または複数の関心事＝Public API／Private実装／デリゲート準拠が混在するファイル）は、`// MARK: -`コメントで区切り、対応する設計書の章番号をあわせて記載する。1〜2メソッド程度の小さな単一責務ファイルでは、MARK分割を省略してよい。

## 5. 命名早見表（実例）

| 分類 | 接頭辞・パターン | 実例 |
|---|---|---|
| ViewController | `<画面名>ViewController` | `ConnectionViewController` |
| 機能レイヤークラス | 要件定義書の処理名を英語化 | `DataReceiver` |
| 役割レイヤークラス | `<役割>Session` | `BluetoothCentralSession` |
| デリゲートプロトコル | `<型名><通知内容>Delegate` | `BluetoothManagerConnectionDelegate` |
| Bool | `is`/`has` + 状態 | `isReceiving` |
| イベント通知クロージャ | `on` + イベント名 | `onFailure` |
| ボタンタップハンドラ | `didTap` + 対象 | `didTapSend` |
| グローバル状態アクセス | `型名.shared.プロパティ` | `StatusManager.shared.status` |
| 名前空間enum（インスタンス不要） | `型名.プロパティ` | `BluetoothGATT.serviceUUID` |
| 状態遷移の実行 | `型名.shared.apply(イベント)` | `StatusManager.shared.apply(.dataSendStarted)` |
