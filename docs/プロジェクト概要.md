# プロジェクト概要.md

このファイルは、`CLAUDE.md`が参照する、本プロジェクト（Sample App）固有の情報をまとめたものである。`CLAUDE.md`に定める共通の役割・責務と組み合わせて、本プロジェクトでの作業に必要な前提知識を提供する。

`CLAUDE.md`の共通ルールを他プロジェクトへ流用する場合、本ファイルはSample App固有の情報であるため流用対象に含めない。新しいプロジェクトでは、本ファイルに相当する固有情報ファイルを別途用意する。

## 1. このプロジェクトについて

- **Sample App**：iPad／iPhoneを1:1でBluetooth接続し、データ送受信を行う検証用アプリ。
- 開発ツールは**Swift Playgrounds**（Xcodeは使用しない）。UIフレームワークは**UIKit**（SwiftUIは使用しない）。
- 唯一の一次情報源は `docs/design/要件定義書.md`。すべての設計書（PS/SS/UI設計書）・コーディング規約・ソースコードのコメントは、この要件定義書の章番号を引用している。

## 2. まず読むべきドキュメント（この順序で）

1. `docs/design/要件定義書.md` — 何を作るかの一次情報
2. `docs/design/PS設計書.md` — 内部処理仕様（状態遷移、通信フォーマット、クラス構成）
3. `docs/design/SS設計書.md` — 画面仕様（ボタン操作、ダイアログ文言、処理順序）
4. `docs/design/UI設計書.md` — 画面レイアウト
5. `docs/コーディング規約.md` — 命名規則・アーキテクチャ方針・ファイル構成ルール
6. `docs/design/操作説明書.md` — エンドユーザー向け操作手順（実装した挙動の答え合わせに使える）
7. `docs/design/開発環境書.md` — 開発者・試験担当者向けの環境構築／ビルド／マージ／E2E試験環境の手順（本ファイルと一部重複するため、変更する場合は両方の整合性を確認すること）

## 3. 要件定義書の扱い

`docs/design/要件定義書.md`はすべての設計書・コードの一次情報であり、`CLAUDE.md`1.2節の原則（一次情報源となる文書は特に慎重に扱う）が具体的に適用される対象である。要件に関わる変更・追加を行う場合は、要件定義書の更新が必要かどうかを都度確認する。更新が必要と判断した場合も、要件定義書を無断で直接書き換えるのではなく、まずユーザーへ変更案をサジェストし、承認を得てから 要件定義書 → PS/SS/UI設計書 → ソースコード の順に反映する。ソースコードだけを直して設計書を放置することも避ける。

## 4. アーキテクチャ・命名規則

`docs/コーディング規約.md` に従うこと。特に以下は繰り返し重要視されてきた方針であり、レビュー時にもこの規約への準拠を確認する。

- **役割（何で通信するか）と機能（何をするか）の分離**：`BluetoothCentralSession`/`BluetoothPeripheralSession`（役割レイヤー）と、`ConnectionStartHandshake`/`ListenStartHandshake`/`Disconnector`/`DataSender`/`DataReceiver`（機能レイヤー）を混在させない。
- **状態遷移の一元管理**：状態（`AppStatus`）を書き換えられるのは `StatusManager.apply(_:)` 経由のみ。個々の処理が直接ステータスを代入しない。
- **1クラス1責務**：ただし、要件定義書上のごく小さな処理（例：`AppInitializer`）まで機械的に新規クラス化すると、将来的にファイル数だけが増えていくリスクがある。新しい処理を追加する際は、「本当に専用クラスが必要か」「既存クラスへの追加で十分か」を都度検討すること（詳細は2026-08-15のレビュー記録を参照。このレビュー内容自体は本ファイルには転記していないため、疑問があれば `docs/design/PS設計書.md` の改訂履歴・関連コミットログを確認すること）。
- **すべての型・主要メソッドに`///`コメントで対応する設計書の章番号を明記する**（トレーサビリティ）。

## 5. Package.swift とルートディレクトリ構成について

- リポジトリ直下（プロジェクトルート）は `Package.swift` / `README.md` / `Sources/` / `docs/` / `CLAUDE.md` のみに保つ方針。
- **`Package.swift` はSwiftPM／Swift Playgroundsのマニフェストファイルであり、必ずプロジェクトルート直下に置く必要がある。** `Sources/`配下など別の場所へ移動するとプロジェクト自体がビルド不能になるため、絶対に移動しないこと。
- `Package.swift`の内容（`.iOSApplication`宣言、`capabilities`、`supportedInterfaceOrientations`等）については、現時点では設計書側に説明がない。変更する場合は、可能であれば要件定義書またはPS設計書側にも根拠を残すことが望ましい。レビュー時も、この種の周辺設定ファイルの内容が設計書側に説明されているかを確認する。

## 6. このセッション（クラウド環境）でのビルド確認について

- **この実行環境には Swift ツールチェインがインストールされていない**（`swift build` 等のコマンドは使用不可）。実際のビルド確認は、ユーザー側のSwift Playgrounds環境でのみ可能。
- そのため、コードの正しさはコンパイラに頼らず、型・シグネチャ・呼び出し関係を目で追って確認すること。特に以下は要注意：
  - アクセス修飾子（`private`のまま他ファイルから呼べなくなっていないか）
  - クロージャのキャプチャ（`[weak self]`の付け忘れによる循環参照）
  - Optional周りの強制アンラップ
- 変更後は、関連するコメント（`///`の章番号）・設計書の記述・コーディング規約との整合性を必ず確認すること。

## 7. 調査用の一時的なログについて

不具合調査のためにコンソールログ等の調査用コードを追加する場合、**必ず`// TEMP-LOG`というコメントタグを同じ行に付け、後から`grep`等で一括して見つけて削除できる状態にすること。** 調査が終わったら、原因を報告した上で、このタグの付いたコードを全て削除する（ユーザーの明示的な指示なしに調査用ログを残したままにしない）。これは特定の調査に限らず、今後同様の調査を行う場合に常に適用する恒久的な運用ルールである。
