## 4. 概要

### 4.1 目的

本書は、Sample App（Bluetooth通信アプリ、アプリ内表示名: Sample App for BlueCom）が、要件定義書・PS設計書・SS設計書・UI設計書に定義された仕様通りに動作することを、**実機2台を用いたE2E（End to End）試験**によって確認するための試験仕様書である。

要件定義書13章に記載の通り、本アプリは単体試験・統合試験用の専用テストコードを持たない方針であり、試験はすべて実機2台によるE2E確認に一本化されている。本書はそのE2E試験の内容を定義するものである。

### 4.2 試験対象範囲

本試験は、以下を1つのシステムとして、実機2台を用いて確認する。

- アプリケーション本体（`Sources/`配下の全ソースコード）
- iOS標準フレームワーク（Core Bluetooth、UIKit）とアプリケーションの結合部分
- 2台の実機間で実際に成立するBluetooth Low Energy通信そのもの

具体的には、TOP画面表示から、Bluetooth接続画面での自端末ID／接続先ID入力、「接続開始」／「待受開始」によるBluetooth通信開始処理・待受開始処理、データ送信画面／データ受信画面での実際のデータ送受信、「戻る」ボタンによる通信切断、予期しない切断からの復帰まで、要件定義書1〜12章および対応するPS/SS/UI設計書に定義された機能の一連の流れを対象とする。

### 4.3 試験対象外の範囲

- ソースコードレベルの単体試験・統合試験（要件定義書13章の方針により実施しない）
- Swift Playgroundsのプレビュー環境のみで完結する確認（実機2台間の実際のBluetooth通信を伴わないため、本書のE2E試験としては扱わない。ビルド時の確認手順は`docs/開発環境書.md`3章を参照）
- TestFlightの配布・証明書設定等、試験環境を構築するまでの手順そのもの（`docs/開発環境書.md`4章を参照。本書はその環境が構築済みであることを前提とする）

### 5.5 各種設定

| 項目 | 内容 |
|---|---|
| Bluetooth | 2台とも試験開始前にオンにしておくこと（操作説明書2章） |
| Bluetooth使用許可（アプリ内） | 初回起動時にOS標準ダイアログで「許可」を選択しておくこと（SS設計書4.1） |
| 機内モード | オフであること（本アプリの動作要件としての明記は無いが、Bluetooth自体がオフになるため） |

### 5.6 通信構成

| 項目 | 内容 |
|---|---|
| 通信方式 | Bluetooth Low Energy（BLE）による1対1通信（要件定義書1.1） |
| 役割 | 「接続開始」を押した端末がCentral役、「待受開始」を押した端末がPeripheral役（PS設計書0.1 No.3）。役割は固定ではなく操作の都度決まる |
| GATTプロファイル | Service UUID `00000000-0000-0000-0000-000000000001`、Request/DataキャラクタリスティックUUID `00000000-0000-0000-0000-000000000002`（Write）、ResponseキャラクタリスティックUUID `00000000-0000-0000-0000-000000000003`（Notify）（PS設計書5.2。UUIDは暫定値） |
| 通信データフォーマット | 18byte固定長（送信種別1byte・通信種別1byte・送信元ID3byte・送信先ID3byte・入力データ10byte）（要件定義書3章、PS設計書4章） |

### 5.7 試験実施に必要な事前条件

| No | 事前条件 |
|---|---|
| 1 | `docs/開発環境書.md`4章の手順により、試験対象のビルドがTestFlight経由で試験用端末2台にインストール済みであること |
| 2 | 試験用端末2台それぞれで、Apple IDでのTestFlightテスター登録・招待の受諾が完了していること |
| 3 | 試験用端末2台のBluetoothがオンになっていること |
| 4 | 5.1〜5.6の構成が整っていること |
| 5 | 【要確認】試験前に、各端末のアプリを完全終了（Force Quit）してから起動する等の「初期状態に戻す」手順が必要かどうかの指定が無い。特に自端末ID／接続先IDは内部パラメータとしてアプリ起動時（要件定義書10章）にのみ初期化されるため、試験ケースをまたいで前の試験の入力値が残っている可能性がある |

4. **RECV-02／RECV-03の「チェックNGとなる電文」を送る手段**：現在のアプリ機能（データ送信画面）では、常に正しい形式（YAMA/KAWA）のデータしか送信できず、チェックNGを意図的に発生させる手段がアプリ内に無い。以下のいずれかの対応が必要だと考えられる。

   - b) 2台のうち一方の自端末ID／接続先IDを試験の途中で変更し、ID不一致によるチェックNGを発生させる（データの中身自体は正しいまま、IDだけが不一致というケース）
   - c) 本項目は実施不可能な試験として「保留」扱いにする
   どの方針で進めるか判断をお願いしたい。
