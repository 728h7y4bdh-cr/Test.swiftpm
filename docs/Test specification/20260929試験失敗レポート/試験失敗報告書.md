# BlueCom 試験失敗報告書

## 発覚日

2026年9月29日

（個々の試験仕様不備を最初に発見した日ではなく、現行の試験仕様書および試験工程を継続使用できない品質問題であると判断した日）

## 試験失敗の概要

BlueComの設計検査仕様書（全43件）を使用して実機試験を開始したところ、試験手順・判定基準・設計との整合性等に複数の問題が判明した。問題は個別の誤記にとどまらず、試験仕様書を作成・レビューする工程そのものに品質上の欠陥があることを示しており、現行仕様書を正式な試験根拠として継続使用することはリスクが高いと判断した。

そのため、現行の試験仕様書を部分修正して試験を継続する方式は採用せず、現行の試験工程を終了し、試験工程および試験仕様書を1から再構築する。

現行の設計検査仕様書、および試験関連の運用ルールファイル（作成ルール・試験実施ルール・ChatGPT試験運用ルール）は、失敗時点の記録として本フォルダへ保管し、以後の正式な試験根拠としては使用しない。

## 詳細

### 1. 設計と異なる期待結果が試験仕様書へ記載されていた

SEND-01（データ送信正常系）の判定基準には「その後自動的に閉じて次のデータを送信可能な状態に戻ること」と記載されている。しかし設計書（SS設計書）では、送信正常終了時の「データ送信完了」ダイアログはOK操作によって閉じる仕様として明記されており、実装（`CommunicationBaseViewController.presentAlert`／`SendViewController`）もOKボタン付きダイアログを表示するのみで、自動的に閉じる処理は実装されていない。この記述は試験仕様書の初版作成時点（2026年8月31日）から一貫して存在しており、設計書の記載が曖昧だったために生じたものではなく、設計に存在しない動作が試験仕様書作成時に追加されたものである。

### 2. 手動試験で確認できない内容が判定・手順に含まれていた

BlueComの試験では、ログやデバッガによる内部状態確認を正式な試験手段として使用していない。それにもかかわらず、Bluetooth接続の内部的な切断処理完了、通信開始・待受開始処理の内部的な非実行等、試験者が画面表示や操作結果から直接確認できない内容を試験手順または判定基準の対象としている項目が複数存在した（GUARD-01、HS-04、HS-05、CONN-07）。これらは試験の直前または試験中に判明し、その場で試験仕様の修正を要した。

### 3. 判定内容に対応する試験操作が不足していた

「操作可能な状態に戻る」「入力が3桁までに制限される」等を判定しようとしているにもかかわらず、それを実際の操作によって確認する手順が不足している項目が存在した（CONN-04、CONN-05）。いずれも試験を実施した結果、記載どおりの手順では判定基準を確認しきれないことが判明し、試験中に手順・判定基準の追加を要した。

このほか、試験目的欄に他の試験番号を挙げて「〇〇と同じ〇〇について」等と記載し、単独の試験項目として内容が完結していない箇所も存在した（GUARD-02、GUARD-03は試験開始直前に、RECV-03は未実施のまま現時点でも同様の記載が残っている）。

### 4. 複数回のレビューで検出できなかった

試験仕様書は初版作成後、表現の具体化・自己完結性・判定基準の観測可能性等について複数回のレビュー・修正を実施しており、実施記録も残っている。しかし、実際に行われていたレビューは「他試験・設計書への参照表現の削除」「抽象的な判定表現の削除」「理由・背景説明の削除」等、あらかじめ想定した特定パターンの除去が中心であり、各試験項目について

設計根拠 → 試験目的 → 試験条件 → 試験操作 → 観測可能な結果 → 判定基準

を1件ずつ意味的に照合するレビューにはなっていなかった。そのため、具体的に記載されてはいるが設計と異なる内容（1.の例）や、具体的ではあるが実際には観測できない内容（2.の例）が、複数回のレビューを通過して「レビュー済み」「完成」の状態まで残った。

実施済み16件のうち、少なくとも8件（CONN-04、CONN-05、CONN-07、HS-04、HS-05、GUARD-01、GUARD-02、GUARD-03）で、試験直前または試験中に試験仕様の修正を要した。

### 5. 試験仕様書の作成・レビューを担ったAIの役割遂行上の問題

本プロジェクトはSDEMを前提として設計・試験成果物を作成しており、AI（Claude）にも設計・試験仕様書の作成・レビューという役割を与えていた。個別ルールとして明文化されていたかどうかに関わらず、

- 設計書に存在しない動作を独自解釈で補って記載しない
- 試験の期待結果を設計根拠と照合する
- 試験者が実際に実施・判定できる内容になっているか確認する

は、この役割を担う上で本来必要な基本的な品質確認である。今回、これらが複数の試験項目にわたって十分に実行されなかったことも、本件の原因として扱う。これは特定の個人・AIへの責任追及ではなく、工程上・品質管理上の問題として捉える。

## 対応策

- 現行の設計検査仕様書、および試験関連の運用Markdown（作成ルール・試験実施ルール・ChatGPT試験運用ルール）の使用を終了し、失敗時点の記録として本フォルダ（`20260929試験失敗レポート/`）へ保管する。
- 現行43件を順番に修正して継続使用する方式は採用しない。
- 試験工程および試験仕様書を1から再構築する。
- 新しい試験では、最初に要件・設計から「検査しなければならない対象」を抽出する。
- 抽出した検査対象を基にシナリオテストを中心として再構成し、必要な網羅性を維持しながら試験項目の過度な細分化を避ける。
- 旧43件は新試験仕様書の土台として流用せず、新しい試験構成を作成した後の抜け確認用資料として扱う。
- 新しい試験仕様書では、設計根拠のない期待結果をAIが独自に補完しない。
- 試験開始前に、設計との整合性、試験手順の実行可能性、判定基準の観測可能性を確認する品質ゲートを設ける。
